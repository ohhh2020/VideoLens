# 2026-11-02 Whisper 原生调用卡住修复与复测

## 撤回与重新定位

按用户要求，上一轮新增的低内存缩批、转写心跳、QQ定时阶段提示及插件v1.1.2变更均不保留。更早的卡片和报告图片修复仍保留，插件保持v1.1.1。本轮没有修改AstrBot插件。

重新检查时，系统可用物理内存约11.8GiB，旧服务的4分33秒视频任务仍卡在CTranslate2的`generate`调用，已持续数小时。上一轮观察到的内存压力不能充分解释当前故障，不能继续认定内存不足就是根因。

同一份272967毫秒的音频，在新进程中使用CUDA/float16、batch=4、beam=5及词级时间戳，直接转写7.670秒完成；项目原ASR封装在提前初始化Torch CUDA后8.091秒完成。新隔离实现的单项测试8.205秒完成。原封装未预先导入Torch的另一次测试为22.245秒，包含测量器首次导入Torch的开销，不能用它宣称纯推理加速。

各测试均输出12个语音片段、1704字符；项目原封装和新隔离实现的转写正文SHA-256相同：

```text
29f7a718f729961cc921c5b66fa9c922deae71b95b616b750e51e012a4e3aa9f
```

这说明硬件、权重和已安装的依赖能够正常转写。旧进程原生调用长期不返回是已确认的故障形态；触发它的底层原因尚未稳定重现，不能宣称已经证明是某个驱动版本或DLL冲突。

## 本轮修复

- Windows CUDA Whisper使用常驻子进程，网页进程不持有另一份Whisper权重；保持当前Conda环境、原模型和识别参数。
- 子进程返回真实设备和精度，加载失败仍阻止服务就绪，不允许CPU或其他模型替代。
- 加载默认60秒超时；准备或下一个语音片段默认90秒无返回时，回收本对象创建的转写进程并使分析失败。不会按进程名终止其他程序，也不自动重复分析。
- OOM保留原来的缩批路径；其他CUDA错误回收上下文。用户手动重试会重新加载干净的worker。
- 设备热切换成功后显式关闭旧worker；切换失败保留原设备。隔离及超时选项不改变转写缓存键。
- 不恢复上一轮的资源分档、心跳或QQ定时提示。

## 真实全流程复测

在独立测试目录构建数据库、索引和产物，读取用户已经下载的同一视频，三个本地模型均真实运行，云端使用现有配置。没有操作现有服务、修改业务数据库或发送群消息。

| 阶段 | 实测秒数 |
| --- | ---: |
| 音频抽取 | 0.740 |
| Whisper转写 | 9.623 |
| 画面理解（29帧） | 12.647 |

| 文本总结 | 20.528 |
| 分析墙钟总时间 | **33.457** |

语音与画面并行，总结与索引并行，各阶段不能相加作为总时间。没有复用转写缓存；最终13个切片、29帧、104条向量、2238字符报告，9次云端请求均成功。报告本地转图片另测0.312秒，生成1页，未发送到QQ群。

本次单独加载及预热三个模型为62.032秒，不包含在33.457秒中；已有本地文件不需要重新下载。它不是“从QQ群发指令到收到结果”的完整端到端计时，也不能把原先卡住数小时与健康进程直接计算成加速倍数。

验收产物仅存本机源码外的`VideoLens-runtime/tests/asr-recheck/`，包括各项结果、完整报告、测试日志和报告图片，不上传到Git。
