## 一、背景：两次真实测试的教训

### 测试 1：讲解类视频（BV1X1n66xEBb，5 分 14 秒，口播为主）

**症状**：分析 20+ 分钟；总结只有约百字。

**已定位并修复**（2026-10-24，已合入，测试 20/20 通过）：

| 问题 | 根因 | 修复 |
| --- | --- | --- |
| 重复分析互踩 | 同视频双击提交两条全量流水线，全局推理锁互相排队 | 编排器同 `video_id` 串行锁 + `JobStore` 同源去重回传 task_id + UI 拦截 |
| 有 GPU 全在 CPU 跑 | torch / llama-cpp-python 均为 PyPI 默认 CPU 轮子；ASR 判定被 CPU 版 torch 误导 | `_cuda_usable()` 改 CTranslate2 优先；`scripts/setup_gpu.py` 一键切换；preflight GPU 检查项 |
| 下载重试浪费 | 相对路径被 yt-dlp 拼成 `data\temp\data\videos\...` | `DownloadConfig.from_config` 走 `cfg.path()` 绝对化 |
| 总结太短 | 只喂 8/16 片（复用问答预算）；提示词限"三到五句"；**yaml 提示词从未被编排器接线** | `_summary_budget` 全片预算；提示词重写（≥400 字、逐段覆盖）；`_build_context` 挂上提示词注册表 |

实测效果：同视频重新生成总结 **1063 字、12 段全覆盖**（旧约百字）。

### 测试 2：运动类视频（BV11Lnm6FEQV，6 分 33 秒，足球集锦）

**症状**：1525 秒分析完，总结八段复读 + 自相矛盾（"COM 3:0 胜 MUN，但 COM 进攻被 MUN 拦截"）。

新暴露的三个问题，**均未修复**，是本计划的直接输入：

1. **转写空结果（最严重）**：GPU 修复生效后 ASR 真的尝试了 CUDA（加载成功），
   但 cuBLAS 惰性加载导致**第一次 transcribe 才抛** `cublas64_12.dll not found`
   ——降级链只在加载期生效，转写期无 CPU 回退 → 返回空转录。
   足球视频的解说词是最有价值的通道，它一丢全盘皆输。
2. **稀疏抽帧 + 静帧描述对运动视频结构性无效**：37 场景 / 71 帧 / 35 组推理，
   2B 模型对每对帧的描述几乎全同（"球员奔跑传球"）。两张 448px 静帧
   本来就区分不出一次进攻与另一次进攻。总结器拿到 14 段同质证据，
   只能复读并在结尾幻觉。
3. **场景检测在 CPU 上对高运动视频不可承受**：pyscenedetect 逐帧解码
   603 秒（超过视频时长）。

时间账本：场景检测 603s ＞ 视觉理解 489s（35 组 × ~14s）＞ 总结 300s ＞ 下载 70s。

## 二、核心设计判断

1. **单一固定管线（帧 → caption → 检索）覆盖不了所有视频类型。**
   它适合"画面变化慢、信息长在画面上"的视频（PPT/教程/访谈）；
   对"信息在语音与连续动作里"的视频（体育/vlog/游戏）从根上不成立。
2. **语音优先**：解说/口播是绝大多数视频的第一信息通道。转写失败应当
   先修复转写（CPU 回退、换档），而不是让视觉全量补位烧 8 分钟。
3. **视觉按类型分派**：讲解类 → 低频抽帧；运动类 → 视频段理解（云端）或
   降档记录（本地）。判定信号用现成的场景切换密度，不必上分类器。
4. **云端是档位，不是依赖**：所有云端通道可开关、可回退，本地链路始终保底。

## 三、D 包：止血包（P0，与云端无关的欠账）

| # | 项 | 做法 | 验收标准 |
| --- | --- | --- | --- |
| D1 | ASR 转写级 CPU 回退 | `_from_whisper` 里 transcribe 抛运行库错误且当前设备非 cpu 时：卸载模型、置 `_force_cpu` 标记、按 CPU 计划重载并重试一次 | 模拟 CUDA 转写失败（monkeypatch）后仍能产出转录（非空），warnings 含回退记录 |
| D2 | 视觉描述去重折叠 | `_attach_visuals` 组装证据时，对相同/近似（前缀哈希）的画面描述折叠为"（连续 N 段画面类似：<首段摘要>）"，只保留时间跨度 | 14 段相同描述进总结时，上下文里只出现 1 段描述 + 折叠说明；总结不再复读 |
| D3 | 高运动视频视觉降档 | 场景密度（次/分钟）超阈值（默认 >20/min）时：`frames_per_scene` 降为 1、跳过连续长描述、仅保留关键帧与图像向量 | 足球类视频视觉阶段耗时下降 ≥50%，报告 degraded/warnings 说明降档 |
| D4 | 场景检测提速 | pyscenedetect 加 `downscale` 更激进 + `frame_skip`（按配置）；高密度视频直接走 ffmpeg select 降级档 | 6 分钟 1080p 高运动视频场景检测 ≤90s（CPU） |
| D5 | 云端视觉并发 | 云端 Runner 的调用改并发（3~4 路，网络型不受推理锁约束） | 35 组云端视觉总耗时 ≤ 串行的一半 |

D 包不改变任何对外接口，全部在 `core/models/asr.py`、`core/pipeline/orchestrator.py`、`core/media/scene_detect.py` 内部完成。

## 四、云端 API 接入（P0.5，大部分已内置）

**要接的通道：两个；要开的账号：可以只要一个。**

| 通道 | 用途 | 阿里百炼（推荐起步） | 状态 |
| --- | --- | --- | --- |
| 文本 LLM | 总结、问答生成 | `qwen-plus` / `qwen-max` | ✅ 已内置（设置页"大模型"区） |
| 视觉 VL | 画面/视频段理解 | `qwen-vl-plus` / `qwen3-vl-plus` | ✅ 已内置（设置页"视觉理解"区） |
| 转写 ASR | — | 暂不做云端（修好 GPU 后本地 ~30s） | 本地专用 |

- 两通道同协议（OpenAI 兼容）、同 `base_url`（`https://dashscope.aliyuncs.com/compatible-mode/v1`）、**同一个 API Key**，设置页填两处即可。
- 预期收益（以足球视频为基准）：总结 300s → 5~15s；问答回答 30-60s → 2-5s；视觉（图片模式）489s → 1~2 分钟。
- **隐私边界**：云端视觉 = 关键帧/视频段出本机；云端 LLM = 转录与描述文本片段出本机。沿用 `vl.cloud_enabled` / `llm.mode` 开关粒度，不新增暗门。
- 云 API **不解决**场景检测与转写本地缺陷——D 包仍然必做。

## 五、视频段理解通道（P1，本轮新增的核心构想）

> 结论：加"**分段**吃视频"，不加"整段吃视频"。

### 5.1 为什么是分段

| | 整段吃（整个视频一次发） | 分段吃（按场景剪 5~20s）✅ |
| --- | --- | --- |
| 上传 | 几十上百 MB，需文件托管/公网 URL | 每段 480p 重编码 1~5MB，base64 直接进请求体 |
| 时间戳 | 模型自由发挥，拿不到可靠分段证据 | 段边界=场景边界，天然对齐 clip/引用/毫秒时间戳 |
| 与 RAG | 只能出笼统总结，进不了证据层 | 描述照旧写切片 → 向量/BM25/引用零改动复用 |
| 失败粒度 | 全盘重来 | 单段失败退回抽帧模式，只损一段 |
| 费用控制 | 不可控 | 按段计，可设每视频段数上限 |

### 5.2 设计

- 新增 `QwenVideoRunner`，与本地 GGUF、云端图片两个 Runner 并列挂在 `VlService`
  门面下，**同一接口**（一组画面 → 一段描述），编排器/切片/检索/问答无感知。
- 数据流：场景区间 → ffmpeg 剪段（`-c copy` 快剪优先，超限则 480p/CRF28 重编码
  压到 ≤5MB）→ base64 `video_url` → qwen-vl → 一段含运动语义与画面字幕的描述。
- 关键帧**照抽**（每场景 1 张，供画廊与图像向量），仅描述文本改由视频段产出；
  数据库结构零改动。
- 配置（`vl` 段新增）：
  - `video_mode: auto | frames | segments`（默认 auto）
  - `video_segment_max_s: 15`（超限自动再剪短）
  - `video_segment_budget: 40`（每视频最多段数，超出的场景走 frames）
- auto 分派：场景密度低（讲解类）→ frames 省钱；密度高（运动类）→ segments。
  密度信号复用 D3 的判定。
- 失败回退：单段调用失败（超限/配额/格式）→ 该段退回 frames 模式；API 无
  video_url 能力 → 整体退回 frames。
- 顺带收益：qwen-vl 能读画面烧录的解说字幕，原"OCR 通道"方案（旧 B 方案）被吸收，不再单独立项。
- 成本量级：6 分半视频 20~37 段，每段几厘~几分钱，单视频 ≤ 几毛钱；D5 并发后延迟 1~2 分钟。

### 5.3 风险与对策

| 风险 | 对策 |
| --- | --- |
| DashScope 视频限制（大小/采样/计费口径）随版本变化 | 段长做成配置；接入时以官方文档为准核对，不写死 |
| `video_url` 是厂商扩展（非 OpenAI 标准） | 隔离在 Runner 内，能力探测失败自动落 frames |
| 费用失控 | 段数预算上限 + 报告里如实列出"视频段 × N / 帧 × M" |

### 5.4 验收标准

- 足球类测试视频（BV11Lnm6FEQV 重跑）：总结无复读段；主要脉络能区分不同进攻/事件；问答"B 费有哪些镜头"能给出 ≥2 个不同时间区间的证据。
- 讲解类视频在 auto 模式下仍走 frames（费用不升）。
- 断网/无 Key 时自动回退，分析不失败。

## 六、方案 A：内容自适应管线（P2，D 包 + 视频段通道的自然延伸）

- **轻量画像**（分析前 ≤30s）：语音占比（VAD 现成）、场景切换密度（现成）、
  有无字幕轨（下载器已探测）→ 三元组决定策略档：
  - 讲解/访谈（低密度+高语音）：现行管线，视觉低频。
  - 体育/高运动（高密度）：语音为主；云端开 → segments，本地 → D3 降档。
  - 无语音（音乐/演示）：视觉为主，段预算放宽。
- 先不引入显式"视频分类模型"——画像信号够用，避免为分类而分类。
- 画像结果写进 `AnalysisReport`（新增 `profile` 字段），前端可见"这是按什么策略分析的"。

## 七、"随时提问"：现状与扩展

**现状（已可用）**：分析一次后随时可问，五个入口（网页问答页 / CLI `ask` /
HTTP `/ask` / MCP `ask_video` / Obsidian 插件）。链路：问题 → bge-m3 向量 →
三通道混合检索（文本/图像/BM25，RRF 融合）→ 按时间线组装证据 → LLM 回答
带 `[n]` 引用（clip_id + 毫秒区间 + 关键帧）→ 事后证据校验（撕伪造编号、
标记无支撑句）。检索 0-15ms；回答时延取决于 LLM 档位。

**三个边界与扩展项**：

| 扩展 | 内容 | 优先级 |
| --- | --- | --- |
| 跨视频全局问答 | 全库 BM25 + 跨视频向量检索，回答带 `video_id + 时间区间`（需打通向量库按代隔离的限制） | P2 |
| 多轮追问 | 每视频保留最近 N 轮上下文（旧版曾有此设计） | P2 |
| 流式输出 | LlmGateway 已支持流式，补 HTTP SSE 端点，满足需求"首 token ≤ 3s" | P1.5 |

**前提共识**：问答质量上限=证据质量上限。D1 修好转写、视频段通道提升视觉
证据后，问答质量同步起飞，无需单独优化。

## 九、实施顺序与总验收

1. **D 包**（D1-D5）—— 保住本地底线。验收见各表。
2. **云端接入引导**（设置页/README 指引，用户侧注册百炼填 Key）。
3. **视频段理解通道**（QwenVideoRunner + auto 分派 + 回退）。
4. **问答流式端点**（P1.5）。
5. **方案 A 画像分派**（在 1-3 的信号与通道都就位后收口）。

**总验收（两种代表性视频各一）**：
- 讲解类：CPU 全链路 ≤8 分钟 / 云端 ≤3 分钟；总结 ≥800 字逐段覆盖；问答带引用且引用可点验。
- 运动类：转写非空；总结无复读、事件可区分；云端视觉段模式单视频成本 ≤1 元。
